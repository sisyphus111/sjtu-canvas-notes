# 讲义写作规则

你将获得一门课某一讲的本地素材目录：原始 PDF/PPT/PPTX 课件、带时间戳的 SRT 字幕、PPT 切片图片与来源记录。只使用实际存在的素材，不要求补造某种文件名或接口 JSON。

> 粒度检查：下载批次、Canvas 模块和录播节次不一定等于讲义边界。若一批材料包含
> 多份连续编号的主课件，应先按课件编号/真实讲次拆分，再分别写讲义；
> 不得为了匹配文件或批次数量把多讲合并成一篇。

- 原始课件及页码/幻灯片序号。
- SRT 字幕及时间戳；字幕可能有识别或转写错误，不能假设已经人工校对。
- PPT 切片图片、切片清单及时间定位。
- 课程名、视频 ID、讲次/日期等来源信息。

## 素材准备

已有本地素材时直接阅读。需要下载时按 [资源获取说明](resources.md) 使用 submodule 中的 CLI；环境准备见 [README](../README.md)。若图片链接已经过期，应通过资源工具刷新切片并下载到本地，再检查讲义引用的图片路径。

请先逐讲阅读这些素材，再为学生直接写一份“从零学会这一讲”的中文学习文档。不要使用固定生成器把字段套进模板，也不要只是复述字幕。只有课件时标明“基于课件”，不将补充背景写成老师在课堂中讲过的内容。文档需要：

1. 先说明这一讲要解决什么问题，以及为什么这些问题值得学习。
2. 按概念依赖关系组织内容，而不是机械按时间线组织。
3. 对每个核心概念回答“是什么、为什么需要、如何工作、容易误解在哪里”。
4. 把课件中的术语、图示线索和课堂字幕中的口头解释结合起来。
5. 保留关键细节、例子、公式或系统设计取舍。
6. 最后给出本讲知识地图、复习问题和下一讲衔接。

核心原则是**宁多勿缺、证据优先、从零可读、覆盖审计优先于篇幅压缩**。最终讲义必须主要围绕课件和课堂回放展开，而不是围绕已有旧笔记、平台概要或模型自己的泛泛知识展开。已有旧笔记只能作为“不要漏掉哪些章节”的参考，不能当作事实来源；如果旧笔记和课件/回放冲突，以课件和老师在回放中的明确解释为准。

## 覆盖审计硬要求

写最终讲义前，先完成一次可检查的“覆盖审计”：逐条检查本讲可用的课件页面、PPT 切片图片/OCR、课件正文标题与要点、课堂字幕中的老师解释。将来源页码/时间段、对应正文位置与缺口记入课程现有来源记录，或课程目录的 `sources.md`；最终讲义不一定要公开列出审计表，但必须体现审计结果：

1. **PPT/课件截图覆盖所有有用信息。** 不允许只挑几张“看起来关键”的图做装饰。每张包含新概念、新机制、新例子、新表格、新公式、新路径、新对比、新实验要求或新结论的课件图，都必须在正文中被覆盖：要么插入本地图片并解释，要么在正文里完整转写和讲解其信息。可以跳过的只有封面、桌面误截、完全重复页、过渡页、无新增信息的标题页；如果一页看似重复但新增了箭头、状态、条件、数字、反例或老师讲解重点，就不能跳过。
2. **文字细节不得低于课堂讲解粒度。** 字幕不是用来压缩成一两句概要的，而是正文细节的下限。老师在课堂中给出的具体例子、类比、反问、错误后果、修复依据、性能数量级、工程取舍、历史背景、应用期望、实验提醒，都要转化成清晰讲义文字。不要把一段 2-3 分钟的解释压成一句“这说明 X 很重要”。
3. **图片解释不能替代正文学习。** 即使把所有 Markdown 图片删掉，只保留文字，读者也应能从零学会本讲主线、术语、机制路径和失败场景。图片用于承载原课件证据和帮助定位图示关系；正文必须独立讲清楚图里的对象、箭头、状态、条件和结论。
4. **截图下方解释要逐对象、逐关系说明。** 对流程图，要说明每个节点是什么、箭头表示什么、正常路径和异常路径分别怎样走；对表格，要解释每一列的含义、各行差别、为什么某些情况安全而某些情况危险；对公式和计算，要解释变量、单位、代入步骤和结果含义。
5. **宁可拆成长讲义，不要用摘要掩盖缺口。** 如果本讲课件/字幕信息多，就把正文拆成多个小节继续写。不要因为篇幅长而省掉课上讲过的动机例子、边界条件、修复逻辑或实验细节。
6. **保留课堂中“为什么”的链条。** 课件标题常常只写结论，字幕里会解释为什么旧方案不行、为什么这个状态危险、为什么某个修复以某个对象为准、为什么性能不可接受。最终讲义必须把这些因果链写出来，而不是只列结果。

素材优先级为：完整课件正文和课件图片 > PPT 切片图片与 OCR > 回放字幕中老师明确解释 > 平台概要/关键词。平台概要只能辅助定位内容，不能替代正文讲解。无法从素材确认的地方要明确写“不确定，需要回看原课件/视频”，不要把推测写成确定事实。

对于课件中的解释图、流程图、状态转换图、体系结构图、表格、公式页、对比图、例题页和包含课堂主线推进的信息页，必须优先保留。写作时要先检查实际下载的 PPT 切片图片、导出记录和原始课件文件：如果某张图承载了有用信息，就在讲义中用 Markdown 图片语法插入本地路径，并在图片下方解释图中每个重要对象、箭头、状态或比较维度。图片不能只贴不讲；也不能只写“见图”而省略机制。若图片未下载或路径不可用，必须保留“建议插入/回看哪一页或哪个时间点”的说明，并尽量用文字或 ASCII 图补足，但要标注这是重画/概括而不是原图。

操作系统这门课尤其要按“问题 -> 抽象 -> 机制 -> 数据结构/状态 -> 运行路径 -> 失败或边界 -> 考点”的链条写。讲到重要机制时，必须写清：

- 它解决的具体失败场景或工程痛点，例如权限越界、地址空间冲突、并发竞态、崩溃后元数据不一致、虚拟机敏感指令陷入、I/O 设备绕过隔离等。
- 它维护哪些对象、状态和不变量，例如页表项、VMA、PCB/TCB、run queue、inode、dentry、journal transaction、VMCS、EPT、namespace、cgroup、SELinux label。
- 一次典型操作的控制流和数据流，例如系统调用进入内核、page fault 处理、context switch、锁竞争、条件变量等待/唤醒、文件读写穿过 VFS/page cache/block layer、VM exit、virtio I/O、容器资源限制生效。
- 关键数据结构保存什么字段，这些字段如何被查找、更新和校验。
- 并发、崩溃、攻击、性能瓶颈或异常输入下会发生什么。
- 它与相邻机制的区别，例如 trap/exception/interrupt、process/thread/coroutine、mutex/semaphore/condition variable、journaling/CoW/soft update、shadow page table/EPT、VM/container、DAC/MAC/RBAC/capability。

考点整理要嵌入正文或文末复习区，但不能凭空编造“老师一定会考”。可以写“容易成为考点/适合出题的理解点”，并把它落实成可检验的问题：画路径、解释为什么、比较机制、推演一个异常场景、说明不变量如何保持、分析性能/安全取舍。不要只列名词表。

如果课程涉及数学、计算、公式、实验数据或定量推导，讲义必须把这些内容当作正文的一部分，而不是只写概念解释。重要公式要用 Markdown/LaTeX 展示，逐一解释变量含义、适用条件、推导直觉和计算步骤；课堂或课件中出现的关键数值例题、矩阵/向量运算、概率/复杂度/性能计算、单位换算、图表读数等，都要在讲义里走一遍。不要把“公式较复杂”作为省略理由；如果材料里公式 OCR 不完整，要结合课件上下文尽量复原，并明确标注不确定处。

数学公式定界符使用 Markdown 常见写法：行内公式写成 `$...$`，块级公式写成 `$$...$$`。不要使用 `\(...\)` 或 `\[...\]`，因为部分 Markdown 阅读器不会渲染这种定界符。

## 风格硬要求

讲义写作由 agent 直接完成，而不是由固定 Python 生成器完成。资源工具负责取得课件、字幕和图片；最终学习文档必须建立在对本讲素材的逐讲阅读和判断上。每一讲可以有不同结构，取决于课程内容本身。

生成结果必须是“可直接阅读并学习”的讲义，不是索引、提纲或概念卡片。不要只写两三句定义，也不要只列“课堂时间轴/关键词/对应课件”。这些信息可以出现，但只能作为辅助材料，正文必须承担教学任务。

不要把下面的检查项机械变成固定栏目。尤其不要每讲都堆出“关键词、课堂时间轴、课件线索、字幕提示、本讲要解决的问题、从问题到机制、核心概念详解、把本讲串起来、你应该能画出的图、易错点、自测问题、学习建议”这种全家桶。格式越多，正文越容易变空。

更好的写法是一篇叙述式补课讲义：先用几段讲清这一讲为什么存在，再把必要术语扫清，然后直接进入机制。时间轴、课件标题、字幕摘录只放在文末作为“回看材料时看哪里”，不能占据正文前半部分。不要反复使用“现实约束带来系统问题，系统问题逼出抽象，抽象再落实成具体机制”“它不是一个孤立名词”“这是一块关键拼图”等套话。

正文里可以用小标题，但小标题必须服务于内容，而不是服务于模板。对于每个核心机制，优先写成连续段落：

- 这个机制用来解决什么具体失败场景。
- 它维护哪些对象和状态。
- 一次典型操作从应用/硬件事件进入系统后，按什么路径执行。
- 关键数据结构里保存什么。
- 失败、并发、崩溃或攻击场景下会怎样。
- 它和相邻机制容易混淆在哪里。

如果这些内容已经在正文里讲清楚，就不要再额外重复“是什么/为什么/如何工作/例子/代价”五个小标题。

默认读者**完全没有上过这门课**，也不能假设读者已经知道课程里顺手提到的工程术语。凡是正文中第一次出现的关键术语，都要用普通语言解释一遍，再继续使用。不要用一个陌生词解释另一个陌生词。

只要不是非常边缘、只在课件角落出现一次且不影响主线的名词，第一次出现时都要给出一两句话的严谨定义。定义不能只是翻译英文；要说明它在系统里扮演什么角色、和本讲主问题有什么关系。之后再进入更长的机制说明。

特别注意：不要把多个陌生词、宏名、寄存器名、标志位或数据结构字段挤在同一句话里。凡是出现“某代码设置 A、B、C、D 等标志，表示若干属性”这类写法，都必须拆开解释。正确顺序是：

1. 先用普通语言说清这段机制的目标。例如“内核要建立一条从高虚拟地址到真实物理内存的翻译路径”，而不是一上来罗列 `KERNEL_VADDR`、`TTBR1`、`L0/L1/L2`。
2. 再解释每一层对象之间的关系。例如多级页表要先说明“上一级页表项保存下一级页表页的位置，最后一级或 block 项才真正给出物理页/物理块地址”，然后再引入 `boot_ttbr1_l0`、`GET_L0_INDEX`、block descriptor 等名字。
3. 对标志位要按角色分组解释：有效性与页表项类型、内存类型与缓存属性、共享/一致性属性、读写执行权限、访问/脏页追踪等。每个重要标志至少说明“是什么、为什么需要、如果没有或设置错会怎样”中的前两项。
4. 一句话里如果超过 3 个新术语，就拆成列表、短段落或小例子。不要写“`UXN`、`ACCESSED`、`INNER_SHARABLE`、`NORMAL_MEMORY`、`IS_VALID` 等表示该块有效、普通内存、共享属性和执行权限等”这种结论式罗列；要分别解释 `IS_VALID` 让硬件知道条目可用，`NORMAL_MEMORY` 告诉硬件按普通可缓存内存处理，`INNER_SHARABLE` 约束多核缓存一致性范围，`UXN` 限制用户态取指等。
5. 讲代码路径时优先用“先发生什么、谁查谁、查到后得到什么、失败时走哪里”的控制流解释，再补符号名和字段名。标识符服务于理解，不要让读者先背标识符再猜机制。

例如，写到服务网格时，不能直接说“业务服务通过 sidecar 或透明代理完成 mTLS、重试、熔断、路由、观测”。必须先解释：

- sidecar 是什么：和主业务容器部署在同一个 Pod/进程邻近位置的辅助代理，像“贴身助手”一样接管进出流量。
- proxy/代理是什么：调用方以为自己在直接访问目标服务，其实请求先经过一个中间组件，由它转发、记录或改写。
- mTLS 是什么：通信双方都拿证书证明身份，并建立加密连接；它不只是 HTTPS 加密，还要求客户端和服务端都互相认证。
- 重试、熔断、限流、灰度发布、服务发现、控制面、数据面分别解决什么问题。

其他类似术语也一样，例如 API Server、etcd、Informer、SharedInformer、Workqueue、reconcile、CRD、Operator、CNI、CSI、PV/PVC、RBAC、GPU kernel、block/thread、KV cache 等。对于操作系统课程，对本讲实际涉及的 kernel、用户态/内核态、特权级、trap/exception/interrupt、system call、ABI、VMA、page table、TLB、ASID、page fault、copy-on-write、buddy system、SLAB/SLUB、PCB、context switch、IPC、condition variable、CAS、futex、cache coherence、inode、dentry、VFS、page cache、journaling、LFS、FTL、NVM、hypervisor/VMM、Guest/Host、VM exit、shadow page table、virtio、IOMMU、namespace、cgroup、seccomp、capability、SELinux、side channel、speculative execution 等术语，也要作相应解释，无须在每一讲重复整份名词表。讲义要像老师在给没听过课的人补课，而不是像给已经懂的人写备忘录。

每讲至少讲清楚这些内容，但不要求按这个名字做栏目：

1. **本讲要解决的问题**：用自然语言讲清楚问题背景。不要只说“本讲介绍 X”，要说“没有 X 会遇到什么困难”。
2. **从问题到机制的推导**：解释为什么旧办法不够，为什么课程引入这个抽象或机制。
3. **先备术语解释**：把本讲后面会用到的陌生词先解释清楚。解释要短但具体，能让学生继续读正文。
4. **核心概念详解**：每个核心概念都要写成一个小节，至少包含：
   - 是什么：给出准确但不空泛的定义。
   - 为什么需要：说明它解决了哪个具体痛点。
   - 如何工作：讲状态、组件、数据流、控制流或算法步骤。
   - 具体例子：用课程实验、云平台、Kubernetes 对象、网络包传输等例子走一遍。
   - 代价和边界：说明它带来的开销、复杂性、失败场景或常见误解。
5. **机制串联**：解释本讲几个概念之间如何互相依赖，不能把它们平铺成互不相关的卡片。
6. **学习检查**：给出能检验理解的问题，问题要迫使学生解释机制，而不是背名词。

密度要求：

- 一讲不能只是 1-2 页“索引”。如果素材足够，每讲应有完整正文，通常应达到数千字级别。
- 对操作系统这门课，素材足够时宁愿写成较厚的补课讲义，也不要压缩成摘要。一般讲次建议至少覆盖“术语铺垫、核心机制、图示解释、路径推演、易错点、复习问题”；复杂讲次可以写到 6000-12000 中文字甚至更多，只要内容来自课件/回放并且组织清楚。
- 每个核心概念不能只有“定义 + 为什么需要”两句话，必须展开到“如何工作”和“例子/推演”。
- 对于系统机制类内容，例如 Controller、CRD、Service、Scheduler、RPC、MQ、Serverless、GPU 等，必须写出运行路径或控制路径。
- 对于课程中出现的英文缩写、系统组件名、业界术语，必须解释其全称或直观含义，并说明它在本讲机制里扮演什么角色。
- 如果课件/字幕中只有标题，不能把标题当正文；要基于课程上下文补出解释，并标明不确定处。
- 对于定量课程或某讲的定量部分，必须保留并解释核心公式。写法不能停留在“该公式用于计算 X”，而要说明公式从什么假设来、每个符号代表什么、代入时单位如何处理、结果如何解释、常见错法在哪里。公式、表格和字符图可以混合使用；必要时用简单数值例子帮助读者真正算一遍。

负例：

```markdown
### Controller 是 Kubernetes 的自动化运维单元

控制器 watch 对象变化，比较期望状态和实际状态，然后采取动作。

**为什么需要它：** 理解 controller，就理解了 Kubernetes 为什么能在故障后自动恢复。
```

这个写法太短，只是概念卡片。正确写法必须继续解释：Controller 如何通过 API Server、Informer/SharedInformer、Workqueue、reconcile 循环工作；Deployment 创建时 Deployment Controller、ReplicaSet Controller、Scheduler、kubelet 如何协作；为什么 Controller 逻辑要幂等；它和 CRD/Operator 有什么关系。

如果素材之间冲突，优先级为：课件正文 > 字幕中老师明确解释 > 平台概要。无法确认的地方请标注“不确定，需要回看原视频/课件页码”。
